# 104 — worm wheel on a sliding saddle

The catalog's `#/movement/104` route offers both arrangements described in
[Brown's caption](https://507movements.com/mm_104.html). With the slide held,
the screw turns the wheel. With the screw held, turning the wheel moves the
slide along the bed. MuJoCo solves the passive output through an **ideal gear
constraint**; Three.js displays the matching helical surfaces. Individual
tooth contacts, friction, backlash and impacts are not simulated.

The former model paired a round wire thread with unrelated wheel teeth. Its
0.6-unit worm pitch exceeded the wheel's circular pitch by 23.2%. It also
placed the pedestal behind the wheel and added unsupported mounting details.
The replacement restores the front pedestal, bored journal, cast rib and
integrated foot, and completes the cropped worm and bed ends.

## Source dimensions and generated teeth

One model unit represents 100 engraving pixels. Independent ink-run readings
from `public/engravings/mm_104.png` determine a 30.3393-pixel worm pitch,
89.4004-pixel wheel tip radius, 73.6843-pixel root radius and 104.9439-pixel
axis separation. The worm root and tip radii are 15.8195 and 27.3844 pixels.
The bearing and shaft are recentered by about one pixel to share the wheel
axis. The foot and bed boundaries retain their measured positions.

The drawing's wheel tooth spacing is irregular. Eighteen uniformly spaced
teeth preserve the measured pitch, wheel diameter and axis spacing with a
short wheel addendum. This tooth count is a reconstruction, not an established
count of hidden teeth in the engraving. The worm uses a straight axial
trapezoid with an inferred 20-degree pressure angle. Its circular pitch
matches the wheel exactly.

The wheel is generated by sweeping the matching helical cutter through a
synchronized rotation, following the [hob-generated worm-wheel construction](https://khkgears.net/product-category/worm-gear-pair/).
The cutter's extra tip height provides the drawn root relief while continuing
the same working flank. A 0.04-pixel radial reduction supplies geometric
clearance. This relief is distinct from backlash, which the ideal transmission
omits. The wheel is a complete bored solid with curved, throated teeth.

The checked-in `wheel-data.js` stores one periodic tooth at 192 angular by
32 axial intervals. Generation uses 1280 phase intervals, 128 radial search
intervals and subsequent root refinement. Doubling the search resolution
changes shared samples by less than 4e-13 source pixel. The coarse and fine
grids differ more between shared samples near steep root transitions; this
check establishes search consistency, not a continuous surface-error proof.

Source comparison uses the actual rendered crest edges and projected wheel
envelope, separately from the input motion law:

| Feature | Samples | RMS distance | Maximum distance |
| --- | ---: | ---: | ---: |
| Pedestal silhouette | 181 | 1.4050 pixels | 3.9311 pixels |
| Front helical crest | 147 | 2.4286 pixels | 6.8040 pixels |
| Nearest wheel silhouette | 373 | 5.1629 pixels | 11.1936 pixels |

The wheel's radial residual is larger: 11.3825 pixels RMS and 17.3604 maximum.
Regularizing its tooth spacing, matching the worm and inferring its depth
require this visible correction. The source overlay exposes it. The true
helical projection also replaces the drawn straight diagonals.

Ten closed solids form the worm, its integral end journals, wheel, shaft,
pedestal, rib, foot, guide key and bed. The inferred retaining key fits a
T-slot with 0.3-pixel side clearance; the foot clears the bed by 0.2 pixel.
The pedestal clears the wheel face by 0.6 pixel. All ten solids pass closure,
orientation, positive-volume and degenerate-triangle checks. Shaft support,
the hidden guide, depth, pressure angle and the completed ends remain explicit
reconstruction assumptions. The worm's omitted supports are ideal bearings.
Fog and ground are disabled.

## Native transmission and controls

There are three scalar coordinates: worm angle `φ`, carriage position `x`
and wheel angle `θ`, measured from the assembled source phase. For lead
`l = pitch/(2π)` and wheel pitch radius `R = 18*l`, the coupling is:

```
x + l*φ - R*θ = 0
```

A MuJoCo [fixed tendon](https://mujoco.readthedocs.io/en/stable/XMLreference.html#tendon-fixed)
forms that linear combination; a [tendon equality](https://mujoco.readthedocs.io/en/stable/XMLreference.html#equality-tendon)
holds it at zero. A second active equality holds either the carriage or worm.
Only the selected input's motor gains are enabled. No output position is
written during stepping, and there is no periodic state correction.

Both arrangements have an eight-second advance/return cycle with smooth
reversals. The screw advances three turns, turning the wheel by 60 degrees.
The wheel-input arrangement advances 40 degrees, moving the carriage by two
worm pitches, about 60.68 source pixels. The direction then reverses. This
drive waveform is inferred; Brown does not specify a stroke or speed.

Mass and full inertia are integrated from the visible solids at one uniform
density. Defaults use gravity, a 2 ms timestep, implicit integration and
4 ms equality response. Guide friction is an inferred 0.05 force unit.
Disabling the transmission constraint leaves the passive output stationary
with gravity disabled while the selected input moves. Independent positive
and negative static loads produce the expected input reaction: wheel torque
divided by 18, or carriage force multiplied by wheel pitch radius. These are
ideal transmission reactions, not calibrated tooth forces or self-locking
behavior.

All four mechanism tests and eleven selected runtime/engine/camera tests pass.
All four existing 031 worm-drive tests also pass after the shared worm geometry
gains optional dimensions and phase. Its previous defaults are preserved.
Ten uninterrupted cycles in each input mode are checked at every timestep:

| Measurement | Screw input | Wheel input |
| --- | ---: | ---: |
| Maximum mesh-phase residual | 0.001944 pixel | 0.000052 pixel |
| Minimum foot retention on bed | 76.6818 pixels | 15.9561 pixels |

| 2 ms versus 1 ms position difference | 0.035751 pixel | 0.023865 pixel |
| 1 ms versus 0.5 ms position difference | 0.017876 pixel | 0.011932 pixel |

Rotation differences are expressed as travel at the wheel pitch radius.
Eighteen native poses over the first cycles pass 33,097,524 independent
finite-surface samples, with only the intended worm/wheel pair having the
small overlap above. All sampled vertices remain inside the camera bounds.
A separate 65-phase geometric sweep checks 9,048,451 near-mesh samples
against the analytic worm without penetration. These sampled checks do not
prove clearance at every possible configuration. The native model has no
collision geometries; absence of native contacts is not a clearance test.

Fixed-step seeking, restart, mode changes and render-frame partitioning
reproduce the same state. Disposal releases native allocations. The production
build and all twenty MuJoCo browser checks pass, including both inputs,
nested hosting, playback, mobile controls, navigation races, retry and cleanup.
The existing large-chunk and guarded Node-import build warnings remain.

All seventeen final captures are inspected, covering both input modes, limits
and return, the source overlay, front/rear/oblique assemblies, mesh, shaft,
guide and desktop/mobile controls. The full mechanism remains in view, and
the mobile notes can be scrolled to the complete reconstruction statement.
A small normal offset removes shaft-face shadow speckles.

Headless Chrome playback averages 13.87 fps over 8.216 seconds, with mean
physics/update time 0.220 ms and 95th percentile 0.300 ms. Rendering the dense
finite helical surfaces is the performance limitation in this environment;
these results do not establish frame rate on other devices. There are no page
errors or unexpected warnings. The known Three.js deprecation/readback notices
remain. Capture and performance results retain immutable source snapshots
outside Git.

```sh
TMPDIR=/dev/shm npm run build
TMPDIR=/dev/shm npx playwright test tests/e2e/mujoco.spec.mjs --output=/dev/shm/104-browser-results
TMPDIR=/dev/shm PROBE_PREFIX=/dev/shm/104-new-views node scripts/capture-mujoco-worm-saddle.mjs
```

The capture uses an existing Vite server on port 5174. Use fresh output
prefixes, one owned browser at a time, and unchanged source/build files during
capture. `WRITE_MODULE` can name a new output module when regenerating the
wheel data; exclusive creation prevents overwriting existing evidence.
